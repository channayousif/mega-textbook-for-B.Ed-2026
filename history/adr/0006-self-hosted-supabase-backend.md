# ADR-0006: Self-Hosted Supabase Backend on Project-Controlled Infrastructure

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together.

- **Status:** Accepted
- **Date:** 2026-07-18
- **Feature:** 002-authentication
- **Context:** Spec 002's plan.md and quickstart.md were written against Supabase's hosted cloud offering (free tier, `ap-south-1` Mumbai region). Mid-implementation, the owner made an explicit, durability-motivated call: `#decision: we will go with selfhosted backend. we will need it in future also. we must have strong foundations`. This is a hosting-model decision, not an application-architecture one — Supabase self-hosted is the same open-source stack (Postgres + GoTrue + PostgREST + Storage + Kong) as Supabase Cloud, so none of Spec 002's migrations, RLS policies, or client code change. What changes is where that stack runs and what operational obligations follow. The project already operates `www.a2ahs.com` on a Hestia-managed VPS (Ubuntu, 15 GiB RAM, 4 vCPU, 45 GB disk), which — after decommissioning three unused services (`mariadb`, `vsftpd`, `php8.3-fpm`) on this same date — has roughly 12 GiB RAM and 13 GB disk free. The site's own static output is already served from this box via `nginx → apache2:8080`, not Vercel (plan.md's "Target Platform: Vercel" line predates and is independent of this decision — see Constitution v2.2.0's downstream-artifacts note).

## Decision

Run **self-hosted Supabase** (Docker Compose: Postgres, GoTrue, PostgREST, Storage, Realtime, Kong, Studio) on the existing a2ahs.com VPS, alongside the already-running Docusaurus static site and its nginx/apache2 front end.

- **Migrations unchanged.** `supabase/migrations/0001`–`0009` are plain SQL against vanilla Postgres + Supabase Auth conventions (`auth.uid()`, `auth.users`, `SECURITY DEFINER` helpers). They apply identically self-hosted or cloud-hosted — nothing in Spec 002's schema, RLS policies, or triggers is Supabase-Cloud-specific.
- **Client code unchanged.** `src/lib/supabase.ts` talks to a URL + anon key; self-hosting only changes what that URL points to.
- **Networking.** ~~Supabase's self-hosted `docker-compose.yml` exposes Kong on `8000` (HTTP) only~~ — **correction (2026-07-18, found by reading the actual compose file rather than trusting a docs summary)**: this version's `docker-compose.yml` publishes **both** `${KONG_HTTP_PORT}:8000` and `${KONG_HTTPS_PORT}:8443` by default, and `8443` collides with apache2's existing public listener (`ss -tln` confirms `80`/`443`/`8080`/`8443` already bound). Fixed by binding both Kong ports, plus Supavisor's `5432`/`6543`, to `127.0.0.1` only in `docker-compose.yml` — this satisfies "Postgres must never be public" and sidesteps the port collision in one change, since a loopback bind on `8443` doesn't conflict with apache2's bind on the box's `10.0.0.150` interface. **Resolved and live**: `nginx` (a standalone `/etc/nginx/conf.d/api.a2ahs.com.conf`, deliberately outside Hestia's per-domain template system, which regenerates and would silently discard a hand-edited proxy config) terminates TLS for `api.a2ahs.com` using a **Cloudflare Origin Certificate** — not Let's Encrypt, since `a2ahs.com` is Cloudflare-proxied (orange cloud) and an Origin Cert is the standard, HTTP-01-free approach for a proxied origin — and proxies to `127.0.0.1:8000`. Verified end-to-end 2026-07-18: `curl https://api.a2ahs.com/auth/v1/health` with the anon key returns GoTrue's health response through the full `Cloudflare → nginx → Kong → GoTrue` chain, and the full RLS suite (13/13) passes through that same public path.
- **Mail relay is a requirement, not an option.** GoTrue's signup-confirmation and password-reset email (FR-002, FR-004 — both P1) MUST route through a transactional relay (Resend or Amazon SES), not the box's local `exim4`. `exim4` is confirmed live for this domain (MX → `mail.a2ahs.com`) but VPS-IP deliverability to Gmail and other major providers is fragile (no sender reputation, easy spam-folder/rejection); a verification email that never arrives is a broken sign-up from the user's point of view, indistinguishable from a bug. This was raised as a recommendation during implementation and is written here as a binding requirement of this ADR, per the commitment made when it was first flagged.
  **Confirmed severe, not theoretical (2026-07-18)**: this version's self-hosted `docker-compose.yml` ships `SMTP_HOST=supabase-mail` with no such service defined at all — every real `/signup` call 500'd (`dial tcp: lookup supabase-mail: server misbehaving`) until fixed. The RLS test suite never caught this because it signs users up via the admin API, which bypasses GoTrue's mail-sending path entirely; only running the actual e2e signup flow through a browser surfaced it. Added a local-only Mailpit catcher (aliased to `supabase-mail`) so `/signup` stops 500ing during dev/test — this is **not** the production fix described above, it is a same-box test double.
  **Resolved (2026-07-18)**: production relay is live. Domain `edu.a2ahs.com` (a dedicated subdomain, not the apex, to stay isolated from the existing `mail.a2ahs.com` inbox/exim4 setup) verified with Resend (SPF + DKIM via Cloudflare DNS, DNS-only/grey-cloud). A `sending_access`-scoped API key (least privilege — cannot list domains or read sent mail, confirmed by testing) is wired into GoTrue's `SMTP_HOST=smtp.resend.com` / `SMTP_PORT=465` / `SMTP_USER=resend` config. Verified twice, independently: (1) a direct Resend API call from `noreply@edu.a2ahs.com` returned a message ID; (2) a real `signUp()` through GoTrue itself returned `200` with a realistic SMTP round-trip duration (~650ms, not an instant local-catcher response) and no error in `auth`'s logs. First API key created was domain-restricted to the wrong domain (created before `edu.a2ahs.com` finished verifying) and 403'd even after the domain showed "Verified" in the dashboard — resolved by issuing a fresh key explicitly scoped to the now-verified domain, not by waiting longer.
- **Backups are the project's obligation now**, not a platform SLA. Out of scope to solve in this ADR, but recorded as a residual risk (see Consequences) — must be a documented `pg_dump`/WAL-archiving cron before Spec 002 handles anything beyond auth (i.e., before Spec 003's grades/submissions land).

## Consequences

### Positive

- **No hosted free-tier ceiling.** Supabase Cloud's free tier pauses after a week of inactivity and caps rows/storage/bandwidth — unsuited to "we will need it in future also, we must have strong foundations." Self-hosting removes that ceiling entirely.
- **Zero incremental vendor cost.** The VPS is already paid for and was carrying ~2.8 GB of headroom before the trim; the box now has ~12 GiB RAM and 13 GB disk free — comfortably enough for the full Supabase stack alongside the existing site.
- **One relationship, not two.** No new third-party account holds student data; everything stays on infrastructure the project already operates, consistent with Constitution Art. VIII's minimal-data-collection stance.
- **All Phase 1–2 work is unaffected.** The 9 migrations, the RLS test harness, and `AuthContext` were written against the OSS Supabase Auth/PostgREST contract, not a cloud-specific feature — this decision costs nothing already built.

### Negative

- **Docker is not installed on this host today** (`docker: command not found`, confirmed 2026-07-18) — this is the concrete next blocker before any RLS/E2E test in Spec 002 can run against real data. Installing it is an infrastructure task outside this ADR's scope but is now the critical path.
- **Operational burden shifts onto the project.** Supabase Cloud would have handled Postgres upgrades, automated backups, and uptime monitoring; self-hosting means the project now owns all three. Backups in particular are unsolved as of this ADR (see Decision) and become urgent once Spec 003 (grades/submissions) lands.
- **Shared blast radius.** The same VPS now serves the public textbook *and* holds account/auth data. A box-level incident (disk full, kernel panic, compromise) affects both, where a hosted backend would have isolated that risk. Mitigation: this is a single-admin-owned VPS already trusted with the site's TLS keys and mail, so the incremental trust delta is smaller than it would be for a multi-tenant or less-trusted host.
- **New external dependency (mail relay).** Resend/SES is a new account and a new secret to manage — deliberately accepted because the alternative (self-sent mail) is a P1 requirement's silent failure mode, not because it's free.
- **Postgres's public exposure is opt-out, not opt-in.** The stock compose file publishes `5432`/`6543` on the host by default; forgetting to firewall them before first `docker compose up` would put the database itself on the public interface. Documented explicitly above so it isn't rediscovered the hard way.

## Alternatives Considered

- **A. Supabase Cloud, free tier (`ap-south-1` Mumbai)** — the option `plan.md`/`quickstart.md`/`ROADMAP.md` were written against. *Rejected:* pauses after a week of inactivity, caps rows/storage/bandwidth, and the owner explicitly wants durable, self-owned infrastructure ("we will need it in future also") rather than a tier designed for evaluation/small projects.
- **B. Supabase Cloud, paid (Pro, ~US$25/mo)** — removes the free-tier caps. *Rejected:* recurring third-party cost when the existing VPS already has ~12 GiB RAM sitting idle; contradicts the "strong foundations we own" framing of the decision.
- **C. Hand-rolled Postgres + a custom Express/Fastify auth server** — maximum control. *Rejected:* reinvents GoTrue/PostgREST/RLS-policy tooling that Spec 002's 9 migrations and `AuthContext` are already built on; throws away all Phase 1–2 work for a larger, less-audited, self-maintained auth implementation.
- **D. Firebase or another BaaS** — mature hosted alternative. *Rejected:* breaks Constitution Art. V.2 (Postgres Row-Level Security is the authorization model the entire Spec 002 data model assumes); would mean rewriting `data-model.md`, all 9 migrations, and `AuthContext` from scratch for no stated benefit.
