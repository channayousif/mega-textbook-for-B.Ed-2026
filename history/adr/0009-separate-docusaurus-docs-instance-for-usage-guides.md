# ADR-0009: Separate Docusaurus docs instance for usage guides

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Proposed
- **Date:** 2026-07-20
- **Feature:** 004-student-dashboard
- **Context:** Constitution v2.4.0 adds Article X (Documentation for Multiple Audiences, ratified/amended this same session), requiring three distinct, purpose-built documentation surfaces — README (contributors), Student Guide, and Teacher Guide — each written for one reader and never merged into a generic catch-all. Article X.4 mandates the Student/Teacher Guides be "bilingual Docusaurus-rendered pages (reusing the same content pipeline as curriculum material..., ) reachable from in-app navigation for the relevant signed-in role." Neither guide, nor a README, exists anywhere in the repo yet. Article X's own Sync Impact Report names Spec 004/005's dashboards as the natural home for the guides' *initial* authoring, since they are the first features giving students/teachers a workflow substantial enough to document. Spec 004 (student dashboard) is the first feature to trigger this obligation via Article VII's Docs gate ("a shipped spec that changes a student... workflow updates the matching guide... in the same branch"). The existing Docusaurus setup (`docusaurus.config.ts`) has exactly one docs-plugin instance, rooted at `/`, whose sidebar/local-search tuning is built entirely around the curriculum's Semester → Course → Unit hierarchy (ADR-0002) — a shape that has nothing to do with how a usage guide's topics (join a class, submit work, read grades, use the dashboard) relate to one another. This decision fixes where all future guide content (this feature's Student Guide, and a later spec's Teacher Guide) will live, and is not reversible without a URL/navigation restructuring once students/teachers have bookmarked or been taught the guide's location.

## Decision

Add a **second Docusaurus docs-plugin instance**, separate from the curriculum's existing
instance, to host both usage guides:

- **Plugin instance:** a second `@docusaurus/plugin-content-docs` instance (classic preset's
  `docs` option supports only one per preset invocation, so this requires either the preset's
  plugin array form or an additional standalone `@docusaurus/plugin-content-docs` entry in
  `docusaurus.config.ts`'s `plugins` array), with a distinct `id` (e.g. `guides`) to avoid the
  silent instance-merging failure mode noted in this feature's own `quickstart.md`.
- **Route:** `routeBasePath: '/guides'` — clearly separate from the curriculum instance's `/`.
- **Content directory:** a new top-level `guides/` folder (sibling to `docs/`), containing
  `guides/student-guide/` (this feature) and, later, `guides/teacher-guide/` (a future spec).
- **i18n:** reuses the site's existing `en`/`ur` locale configuration — no new i18n setup, since
  Docusaurus applies one `i18n` config across all docs-plugin instances.
- **Search:** the existing `@easyops-cn/docusaurus-search-local` theme instance's
  `docsRouteBasePath` config is extended (or a second theme instance added) to index the `guides`
  route alongside `/`, so guide content remains discoverable through the same offline bilingual
  search Spec 001 already built — without letting guide topics pollute the curriculum's own
  search relevance tuning.
- **Navigation:** a "Dashboard"/guide entry point is exposed via a new swizzled navbar item,
  visible only to a signed-in student (this feature) — not a permanent top-level navbar item
  visible to anonymous visitors, keeping the curriculum catalog as the site's unauthenticated
  home (Spec 001 SC-003).

## Consequences

### Positive

- **No interference with the curriculum's sidebar/search tuning.** The Semester → Course → Unit
  autogenerated sidebar (ADR-0002) and its bilingual search indexing stay exactly as they are;
  guide content gets its own topic-based navigation shape without forcing either instance to
  compromise.
- **One clear, permanent home for all future guide content.** The Teacher Guide (a future spec's
  obligation) slots into the same `guides/` instance with zero new plugin/config work — only new
  content folders, mirroring Constitution Art. V.4's "adding a course must not require
  platform-code change" principle applied to guides instead of courses.
- **Reuses the existing content pipeline exactly as Article X.4 requires** — same MDX rendering,
  same bilingual `i18n` locale machinery, same `custom.css` theme — no new rendering technology,
  no new build step beyond one more plugin-instance entry in `docusaurus.config.ts`.

### Negative

- **A second docs-plugin instance is new surface area to misconfigure.** A missing/duplicate
  `id`, or search-index configuration drift between the two instances, can silently merge or break
  routing (documented as this feature's own quickstart.md failure mode #3) — this is a
  one-time setup risk, not an ongoing maintenance cost, but it must be caught in the Art. VII
  engineering gate (`npm run build` fails loudly on a genuine plugin-id collision; a
  misconfigured-but-non-colliding setup would not).
- **Bilingual search relevance across two instances is unverified for guides specifically** —
  Spec 001's own research already flagged Urdu tokenization quality as an open risk for the
  *curriculum* instance; extending the same local-search theme to a second instance inherits that
  risk without yet having a guide-specific test to confirm results are useful, not just present.
- **A second navbar/route surface for signed-in users** adds one more place a future feature
  could inconsistently gate access (e.g., forgetting the student-only visibility rule when the
  Teacher Guide is added later) — mitigated by treating this ADR's navigation pattern
  (role-gated navbar entry, not a permanent public link) as the precedent for the Teacher Guide too.

## Alternatives Considered

- **A. Fold guide pages into the existing curriculum `docs/` instance**, e.g. under
  `docs/guides/...` with `routeBasePath: '/'` shared with the semester content. *Rejected:* the
  existing sidebar is autogenerated from the Semester → Course → Unit folder structure
  specifically to keep "adding a course = adding folders" true (Art. V.4, ADR-0002); mixing in an
  unrelated topic-based navigational shape (guide-to-guide, not semester-to-course-to-unit) would
  either require hand-maintained sidebar overrides (defeating the autogeneration this repo relies
  on) or would confuse the curriculum catalog that Spec 001's SC-003 establishes as the site's
  home. It also risks the local-search index surfacing guide pages ahead of curriculum content (or
  vice versa) for overlapping search terms, with no clean way to separate relevance tuning within
  one instance.
- **B. Plain static (non-Docusaurus) pages under `src/pages/`**, matching the app-page pattern
  already used for `/app/*` routes. *Rejected:* Article X.4 explicitly requires the guides to
  reuse "the same content pipeline as curriculum material" — i.e., Docusaurus-rendered MDX with
  its bilingual `i18n` machinery, not hand-built React pages. Plain `src/pages/` React components
  would also mean re-implementing locale-aware rendering and RTL support that the docs-plugin
  content pipeline already provides for free.
- **C. A single guides file per locale (no docs plugin at all), e.g. one long
  `student-guide.mdx` rendered via a custom route.** *Rejected:* loses per-topic addressability
  (a student can't be linked directly to "how to submit work"), loses the autogenerated
  next/previous navigation and sidebar Docusaurus's docs plugin provides, and doesn't scale
  cleanly once the Teacher Guide is added — every advantage of using the docs plugin in the first
  place would have to be hand-rolled instead.
