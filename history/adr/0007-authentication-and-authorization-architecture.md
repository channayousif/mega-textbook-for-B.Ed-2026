# ADR-0007: Authentication and Authorization Architecture

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2026-07-19
- **Feature:** 002-authentication
- **Context:** Spec 002 adds the first application state (accounts, roles, sessions) to a site that was previously pure static content (Constitution Art. V.1). This forced a foundational choice with no precedent in this repo: where does authorization actually live, and how does the browser reach it? The static site has no application server and the constitution forbids adding one (Art. V.4/V.6). Two closely-related sub-decisions were made together during Phase 0 research and Phase 1 design and never written up as their own ADR — they were captured only as scattered bullets in `research.md` (R2) and a table in `plan.md`'s Complexity Tracking: (1) the browser talks directly to self-hosted Supabase with the anon key, with **no API/BFF layer**, and authorization is enforced **entirely at the database layer**; (2) role and capability state is read live from the `profiles` table on every check, **never from a JWT claim**, specifically because FR-008 requires an admin's change to apply by the user's "next visit" and FR-011a's long-lived sessions make a cached JWT claim stale for potentially days. ADR-0005 documents the role *policy* (what the rules are) and ADR-0006 documents the backend *hosting location* (self-hosted vs. cloud) — neither covers this: the technical shape of how authorization is actually implemented and enforced, which every future feature that touches roles or permissions (Specs 003–005) must follow.

## Decision

Authorization for this platform is implemented as a **thin, database-enforced model with no application server**:

- **No API/BFF layer.** The browser talks directly to self-hosted Supabase (Postgres + GoTrue + PostgREST) using the public anon key. There is no Node/Express/Next.js API route sitting between the client and the database — the static Docusaurus site plus this direct Supabase connection *is* the whole application.
- **Authorization lives entirely in the database, never the UI.** Row-Level Security policies and `SECURITY DEFINER` trigger functions are the sole enforcement boundary (Constitution Art. IX.2). `AuthGuard.tsx`'s role/capability checks are explicitly cosmetic — they improve UX by hiding controls a user can't use, but a determined client bypassing the UI entirely gains nothing, because the same checks are re-enforced by Postgres on every query.
- **Role and capability state is read from `profiles`, never a JWT claim.** `AuthContext` does a live `SELECT` against `profiles` (columns: `role`, `verified_teacher`, `status`) after establishing a session, rather than trusting `app_metadata`/`user_metadata` baked into the JWT at issuance. This is the one rule in this cluster most likely to look like an "obvious" optimization to a future engineer — a code comment in `AuthContext.tsx` and a dedicated e2e test (`auth-role-propagation.spec.ts`) both exist specifically to catch that regression.
- **A guard trigger enforces column-level write restrictions that RLS cannot express alone.** Postgres RLS can allow or deny an entire row `UPDATE`, but cannot safely express "you may update this row, but not these specific columns." A `BEFORE UPDATE` trigger on `profiles` compares `OLD`/`NEW` on `role`, `verified_teacher`, and `status`, and rejects the change outright unless the caller is an admin — this is what makes "a user cannot grant themselves admin" (FR-006) enforceable rather than aspirational.
- **The service-role key is confined to exactly two Edge Functions** (`admin-suspend`, `delete-account`) — the only two operations that require it (revoking a live session; deleting an `auth.users` row). The key never reaches `src/` or the browser bundle; a build-time guard (`scripts/check-no-service-key.mjs`) fails the build if it ever does.
- **A single, site-wide session.** A `Root` theme swizzle mounts one `<AuthProvider>` around every route — docs and `/app/*` pages alike — so a session established while reading a unit persists into the account/admin pages without re-authentication, and signing out from any page ends it everywhere (FR-011, FR-012).

## Consequences

### Positive

- **Smallest possible attack surface.** With no API server, there is no custom authorization code to audit outside RLS policies and two small Edge Functions — the entire enforcement layer is declarative SQL, reviewable in Git.
- **No server to run, deploy, patch, or scale.** Consistent with the constitution's static-site mandate (Art. V.4/V.6) and the project's self-hosted, cost-controlled infrastructure stance (ADR-0006) — one fewer moving part on a single VPS already carrying the site and the database.
- **Authorization correctness survives UI bugs.** Because RLS is the real boundary, a mistake in `AuthGuard.tsx` (or its complete removal) cannot leak data — the worst case is a confusing UI, not a security hole. This was exercised directly: the RLS test suite (34 tests) asserts negative cases independent of any UI code.
- **Role changes apply immediately, not on next token refresh.** Reading `profiles` live means an admin's change is visible on the user's very next request, satisfying FR-008 exactly — a JWT-claim approach would have made this a function of token TTL instead of a guarantee.
- **Clear separation of "identity" from "access."** The role/`verified_teacher` split (ADR-0005) is only enforceable this cleanly because both are ordinary columns checked by RLS on every query, not claims frozen at sign-in.

### Negative

- **Extra database round-trip per session load.** Every page load that needs role/capability data makes a live `profiles` query rather than reading it for free out of an already-verified JWT. Accepted as the right tradeoff given FR-008's freshness requirement; flagged in `research.md` as revisitable ("MAY be added later as a read-through cache if profile lookups become a latency problem") — not yet needed at the current low-hundreds-of-users scale (plan.md's Scale/Scope).
- **Two hand-written enforcement mechanisms to keep in sync.** RLS policies and the guard trigger must both be correct and are logically separate artifacts (a migration file each) — a change to one without the other could reintroduce the exact column-level bypass the trigger exists to close. Mitigated by `tests/rls/privileged-columns.test.mjs` and `tests/rls/admin-role-change.test.mjs` asserting both together.
- **No app server means no place to put future server-side-only logic cheaply.** Any future feature needing logic that can't be expressed as SQL/RLS (rate limiting, complex notifications, third-party webhooks) will need its own Edge Function, following the same "least privilege, service-role-confined" pattern established here — not a blocker today, but a constraint every later spec inherits.
- **The "don't optimize this into a JWT claim" rule is a tribal-knowledge risk.** It is currently enforced by a code comment and one e2e test, not a structural impossibility — a future contributor unaware of FR-008/FR-011a's interaction could still make the regression, just not silently (the test would fail).

## Alternatives Considered

- **A. Traditional API/BFF server (Node/Express or Next.js API routes) fronting Postgres.** *Rejected*: reintroduces exactly the server the constitution's static-site architecture (Art. V.4/V.6) was chosen to avoid — a new deployable, a new attack surface, and a new thing to keep patched/scaled, for authorization logic Postgres RLS already expresses natively.
- **B. Role/capability stored in JWT `app_metadata`, read from the token.** *Rejected as the source of truth* (research.md R2): this is Supabase's own commonly-documented pattern, but under this feature's long-lived sessions (FR-011a) a claim would persist stale for up to days, directly violating FR-008's "admin's change applies by next visit" guarantee. Not ruled out forever — explicitly left open as a future read-through cache *on top of* the database as source of truth, if query latency ever becomes a real problem.
- **C. RLS policies alone, no guard trigger.** *Rejected* (plan.md Complexity Tracking): Postgres RLS cannot express "this row is writable, but these three columns within it are not" — a policy permissive enough to let a user update their own `full_name` would, without the trigger, also let a crafted `UPDATE` statement smuggle in `role: 'admin'`.
- **D. Suspend/delete performed client-side with the service-role key shipped to the browser.** *Rejected* (plan.md Complexity Tracking): a total compromise of the entire security model — the service-role key bypasses every RLS policy, so shipping it anywhere client-reachable is equivalent to having no authorization layer at all.
- **E. A separate `user_roles` join table instead of columns on `profiles`.** *Rejected* (research.md R2): unjustified complexity for a one-role-per-user v1 (Constitution Art. VI.2, simplicity-first); revisit only if multi-role-per-user becomes an actual requirement.
