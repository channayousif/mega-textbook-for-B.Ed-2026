## Response snapshot

Re-ran the e2e spec after the user confirmed the Playwright system-dependency install; it did
work this time (browser launched, first assertion passed), but the second test failed for a real
reason: `getByText(/check your email/i)` never appeared. The page showed `alert: Something went
wrong. Please try again.` — the `unknown` fallback in `authErrors.ts`, meaning GoTrue returned
something the classifier didn't recognize.

Reproduced directly with a throwaway `node -e` script calling `signUp()` against the live
instance: `AuthRetryableFetchError`, status 500, empty body. Checked `docker compose logs auth`
and found the real cause: `dial tcp: lookup supabase-mail on 127.0.0.11:53: server misbehaving`.
GoTrue's `.env` (generated by `utils/generate-keys.sh` during PHR 0014, defaults left untouched)
sets `SMTP_HOST=supabase-mail`, but this version of the self-hosted `docker-compose.yml` defines
no such service — confirmed by grepping for a `mail:` service block earlier in PHR 0014 and
finding none. Every real `/signup` call was failing with a 500, invisible to the RLS suite
because `tests/rls/*` all sign up via the **admin API** (`auth.admin.createUser`), which bypasses
GoTrue's mail-sending code path entirely. 13/13 RLS tests passing had created false confidence —
the actual, most basic user-facing flow (the MVP's entire point, US1) was completely broken, and
only running the real e2e flow through an actual browser against the real `/signup` endpoint
surfaced it.

Fixed for local/dev testing by adding a Mailpit SMTP-catcher service to
`~/supabase-project/docker-compose.yml` (outside the repo, alongside the rest of the running
infrastructure — not committed), aliased to the hostname `supabase-mail` GoTrue already expects,
with its web UI bound to loopback only. Restarted the `auth` container, confirmed DNS resolution
via `docker compose exec auth getent hosts supabase-mail`, re-ran the e2e spec: both tests pass.
Verified beyond "no error" — queried Mailpit's API directly and confirmed a real
"Confirm Your Email" message was captured for the test signup, not just that GoTrue stopped
500ing. Re-ran the full RLS suite as a regression check after restarting `auth` — still 13/13.

Explicitly did **not** treat this as satisfying ADR-0006's mail relay requirement. Updated the
ADR to mark that requirement "confirmed severe, not theoretical" rather than resolved — Mailpit
is a same-box test double for local signup testing, not a delivery path any real user's email
would ever reach a real inbox through.

- 🧠 Reflection: this is the clearest example yet in this session of "a fully green test suite proving nothing about the thing that actually matters" — 13/13 RLS tests and a passing production build gave every appearance of a working MVP while the literal core user action (sign up with email) was broken end to end. The gap existed specifically because the RLS harness's own design choice (admin API for speed/determinism) quietly excluded the one code path — real mail sending — that was actually broken. Test-suite coverage and user-journey coverage are not the same claim, and this session had been treating them as interchangeable.
