# Phase 1 Data Model: Curriculum-owner console and the content-improvement loop

Two new Supabase Postgres tables extend Specs 002/003's schema (`profiles`, `is_admin()`,
`current_profile_id()`, `touch_updated_at()` all reused verbatim, zero change to any of them).
Plus three file-based, non-database entities (Feedback export bundle, Content-status snapshot,
extended content-index record) generated by scripts and read by the console.

## Table: `self_assessment_checks` (migration `0032`)

One student's tick against one checklist item of one topic in one language (Key Entity
"Self-assessment check"). Identity is positional (research.md R3), never the item's own text.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK, `gen_random_uuid()` |
| `student_id` | `uuid not null references profiles(id)` | never `auth.users(id)` - tombstone-survival convention |
| `course_code` | `text not null` | unvalidated pointer into Git content, same convention as every other course-scoped table since Spec 003 |
| `unit_no` | `integer not null` | |
| `topic_no` | `integer not null` | the `topic_no` front-matter field (contract: `topic-cycle.md`) |
| `locale` | `text not null check (locale in ('en','ur'))` | EN and UR checklists are tracked as separate rows - Assumptions guarantee same count/order, not shared state |
| `item_position` | `integer not null check (item_position >= 1)` | one-based index of the `- [ ]` line within the section, in document order |
| `item_text_snapshot` | `text not null` | normalized (trim + collapse whitespace) item text at the moment this row was last written |
| `checked` | `boolean not null default true` | un-ticking is `checked = false`, never a delete |
| `created_at` | `timestamptz not null default now()` | |
| `updated_at` | `timestamptz not null default now()` | bumped by `touch_updated_at()` (reused, Spec 003 `0017`) |

`unique (student_id, course_code, unit_no, topic_no, locale, item_position)` - the natural key an
upsert targets.

**RLS** (enabled):

- `self_assessment_checks_select` - `using (student_id = current_profile_id() or is_admin())`.
  No teacher branch exists at all - the default-deny means a teacher's query returns zero rows,
  which is how FR-006 ("Teachers MUST NOT have access") is enforced at the data layer, not by
  omitting a UI link.
- `self_assessment_checks_insert` - `with check (student_id = current_profile_id() and
  is_student())` (migration `0036`, added after RLS regression testing found the gap: a
  `student_id = current_profile_id()`-only check says nothing about the caller's *role*, so a
  teacher could insert a row naming their own profile id as `student_id` and then read it
  straight back under the SELECT policy's own `student_id = current_profile_id()` branch -
  `is_student()` (mirrors `is_admin()`'s shape) closes that at the database layer, not only in
  `DocItem/Content.tsx`'s matching client-side role gate).
- `self_assessment_checks_update` - `using (student_id = current_profile_id())`,
  `with check (student_id = current_profile_id() and is_student())` (same `0036` guard - a
  student later promoted to teacher can no longer touch even their own historical rows); a
  guard trigger (below) further narrows which columns an update may actually touch.
- No `DELETE` policy - un-ticking is an `UPDATE` to `checked = false`.

`grant select, insert, update on self_assessment_checks to authenticated`.

**Trigger** `enforce_self_assessment_immutable_identity()` (`BEFORE UPDATE`) - rejects any change
to `student_id`, `course_code`, `unit_no`, `topic_no`, `locale`, `item_position`, or `created_at`;
only `checked`, `item_text_snapshot`, and `updated_at` may move. Same shape as
`enforce_suggestion_status_transition()` (Spec 005, `0031`) minus the transition-graph half - here
there is no status machine, just "the identity columns are frozen after insert."

**Admin aggregate read**: FR-006's "aggregate... per course and unit" is a plain
`select course_code, unit_no, count(*) filter (where checked), count(distinct student_id) ...`
the console runs directly against this table under the admin `SELECT` policy above - no
materialized view or RPC needed at this scale (same posture as every other admin aggregate in
this codebase, e.g. `activityFeedback.ts`'s `fetchAllAggregatedFeedback`).

## Table: `content_feedback` (migration `0033`)

One piece of reader feedback on one content page within a unit (Key Entity "Content feedback
item"). A third, distinct feedback stream alongside Spec 005's `activity_feedback` (teacher
per-activity ratings) and `improvement_suggestions` (teacher-filed, admin-moderated) - see
research.md R8 for why these are not merged.

```sql
create type public.content_feedback_page_kind as enum (
  'topic', 'unit_opening', 'unit_assessment', 'unit_teacher_notes', 'course_review'
);
create type public.content_feedback_scope as enum ('whole_page', 'passage');
create type public.content_feedback_status as enum ('open', 'planned', 'resolved', 'declined');
```

**Guest access (migration `0037`, 2026-09-07 follow-up)**: `author_id` is nullable and a row may
instead carry `guest_email` + `guest_confirmation_token` - a signed-out reader identified only
by a self-reported email, submitted via `guest-feedback-submit` (an Edge Function using the
service role, since an unauthenticated insert needs its own server-side validation this table's
RLS can't express) and confirmed via `confirm_guest_feedback(token)`, a `SECURITY DEFINER` RPC
`anon` may call directly - the token itself is the credential. See "Guest columns" and
"Guest RLS/RPC" below; the original `author_id not null` shape (student/teacher/admin) is
otherwise unchanged.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | PK |
| `author_id` | `uuid references profiles(id)` | **nullable since `0037`** - null on a guest row (`guest_email` set instead); exactly one of the two is ever set |
| `author_role` | `text not null` | **stamped server-side** by trigger from `profiles.role`, or `'guest'` when `author_id is null` - never client-supplied (FR-014) |
| `page_kind` | `content_feedback_page_kind not null` | derived client-side from the page's own path (research.md R6), sent as-is - not itself sensitive, no server stamping needed |
| `course_code` | `text not null` | |
| `unit_no` | `integer` | null only when `page_kind = 'course_review'` |
| `topic_no` | `integer` | set only when `page_kind = 'topic'` |
| `locale` | `text not null check (locale in ('en','ur'))` | |
| `section_anchor` | `text` | nearest heading id at submission time; nullable (top of page) |
| `scope` | `content_feedback_scope not null` | |
| `quoted_passage` | `text check (char_length(quoted_passage) <= 2000)` | required when `scope = 'passage'`, forbidden when `'whole_page'` (check constraint below) |
| `passage_context` | `text check (char_length(passage_context) <= 2000)` | best-effort re-location material (research.md R7); never rendered to the owner as a page-body quote, only used to attempt to re-find the passage |
| `comment` | `text not null check (char_length(comment) <= 4000)` | FR-017 |
| `status` | `content_feedback_status not null default 'open'` | |
| `owner_note` | `text` | set only by the owner, on transition |
| `resolution_ref` | `text` | a change reference (commit/PR), set only when resolving |
| `created_at` | `timestamptz not null default now()` | |
| `updated_at` | `timestamptz not null default now()` | |
| `guest_email` | `text` | **`0037`** - set only when `author_id is null`; format-checked, never verified beyond that plus the confirmation click |
| `guest_confirmation_token` | `uuid` | **`0037`** - set only when `guest_email is not null`; unique; the sole credential `confirm_guest_feedback()` checks |
| `guest_confirmed_at` | `timestamptz` | **`0037`** - null until the guest clicks the emailed link; a triage signal, not a visibility gate (the admin queue shows the row either way) |

Check constraints:

```sql
check (
  (scope = 'passage' and quoted_passage is not null)
  or (scope = 'whole_page' and quoted_passage is null)
)
check ((page_kind = 'topic') = (topic_no is not null))
check ((page_kind = 'course_review') = (unit_no is null))
-- 0037:
check ((author_id is not null) <> (guest_email is not null))          -- exactly one identity
check ((guest_email is not null) = (guest_confirmation_token is not null))
check (guest_confirmed_at is null or guest_email is not null)
check (guest_email is null or guest_email ~* '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]+$')
```

**RLS** (enabled):

- `content_feedback_select` - `using (author_id = current_profile_id() or is_admin())` (FR-015,
  FR-018).
- `content_feedback_insert` - `with check (author_id = current_profile_id() and status = 'open')`
  - a client cannot insert at any status other than `open` (FR-014's "initial status
    server-side").
- `content_feedback_update` - `using (is_admin())`, `with check (is_admin())` - only the owner
  may ever update a row (FR-019); a guard trigger (below) narrows this further.
- No `DELETE` policy.
- **No `anon` policy of any kind on this table** (`0037`) - a guest submission never touches
  `content_feedback` directly; see "Guest RLS/RPC" below.

`grant select, insert, update on content_feedback to authenticated`.

**Guest RLS/RPC (`0037`)**: `confirm_guest_feedback(p_token uuid) returns boolean`, `SECURITY
DEFINER`, `grant execute ... to anon, authenticated`. Updates `guest_confirmed_at = now()` on the
one row matching `p_token` where it is still null; returns `true` on success, `false` for an
unknown or already-used token (never raises - a confirm page can't usefully distinguish "invalid"
from "already used" from a boolean either, which is a documented simplification, not a gap). This
is the *only* way an `anon` caller can affect this table at all - there is deliberately no `anon`
INSERT policy, since the actual guest submission needs server-side validation and an email send
that RLS cannot express (hence `guest-feedback-submit`, an Edge Function using the service role,
covered in contracts/console-operations.md).

**Trigger 1** `stamp_content_feedback_author_role()` (`BEFORE INSERT`, `SECURITY DEFINER`) -
overwrites `new.author_role` with the inserting user's `profiles.role`, unconditionally, so a
crafted `author_role` value in the client payload is discarded regardless of what was sent
(FR-014). **`0037`**: when `new.author_id is null` (a guest row), sets `'guest'` directly rather
than looking up a profile that doesn't exist for this insert.

**Trigger 2** `enforce_content_feedback_status_transition()` (`BEFORE UPDATE`) - same shape as
Spec 005's `enforce_suggestion_status_transition()` (`0031`), adapted to this lifecycle:

- Only `status`, `owner_note`, and `resolution_ref` may change; every other column raises.
- Legal transitions: `open -> planned`, `open -> resolved`, `open -> declined`,
  `planned -> resolved`, `planned -> declined`, `resolved -> open` (reopen),
  `declined -> open` (reopen). A same-status update (note-only edit) is also permitted, matching
  Spec 005's precedent. Any other pair (e.g. `resolved -> planned`, `declined -> resolved`
  directly) raises `illegal content_feedback status transition` (FR-019, "MUST reject
  out-of-sequence transitions").

**Access-control matrix**

| Actor | `self_assessment_checks` | `content_feedback` |
|---|---|---|
| Signed-out visitor | no access (no `anon` grant) | **`0037`**: no direct table access (still no `anon` grant) - submits via `guest-feedback-submit` (own row only, always `author_id null`) and confirms via `confirm_guest_feedback(token)`; cannot select any row back, including their own |
| Student, own rows | select/insert/update own | select/insert own; no update |
| Student, another student's rows | none | none |
| Teacher | **none** (Art. VIII.1, FR-006) | select/insert own (as an author, same as a student); no update; cannot see another reader's rows |
| Admin (curriculum owner) | select all (aggregate); no insert/update of another student's row | select all (guest rows included, confirmed or not); update (status/note/ref) on any row |

## File-based entities (no database)

### Feedback export bundle

Generated on demand by `src/lib/contentFeedback.ts`'s `exportUnitFeedback(courseCode, unitNo)`
(Story 5, FR-022) - never stored. Queries `content_feedback` for
`status in ('open','planned')` scoped to the unit, resolves each row's `(course_code, unit_no,
topic_no, page_kind)` to a repository-relative path via the same filename convention
`report-content-status.mjs` and `build-content-index.mjs` already encode (`topic-NN.mdx` /
`index.mdx` / `unit-assessment.mdx` / `unit-teacher-notes.mdx` / `course-review.mdx` under
`docs/semester-<n>/<course>/unit-<NN>/` or the course root), and renders one self-contained
Markdown document: a heading per affected file (its repo-relative path), then each item's quoted
passage as a blockquote and its comment as prose beneath - no page body text is ever pulled in
(FR-022's "without copying page body text into the export"). Idempotent: an item stays in the
export for as long as it stays `open`/`planned` (FR-024, edge case "exported item not closed").

### The revision procedure (Story 5, FR-023/025)

A new Claude Code skill, `.claude/skills/revise-topic/` (named in the Constitution v2.7.0 Sync
Impact Report's own Follow-up TODOs as this feature's obligation), takes the export document as
input and proposes a minimal, traceable edit to each named file and its translation, then runs
the full content-check set - `validate:content`, `check:depth-gate`, `check:figures`,
`check:no-answer-keys`, `check:no-em-dash` - before presenting the change set for review. This is
process/tooling, not a database or API surface; `quickstart.md` walks the exact sequence.

### Content-status snapshot

Generated by `scripts/report-content-status.mjs` (Story 4, FR-031-033; mechanism: research.md
R9). Written to `static/content-status.json` (same convention as Spec 003's
`content-index.json`) on `prestart`/`prebuild` and as an informational CI step. Shape:

```json
{
  "generated_at": "2026-09-05T10:00:00.000Z",
  "courses": [
    {
      "course_code": "EFMP-302",
      "units": [
        {
          "unit_no": 1,
          "authored": true,
          "translation_status": "draft",
          "depth_check": "pass",
          "figures": { "prompt_only": 0, "generated": 0, "placed": 4 },
          "figures_pending": []
        }
      ]
    }
  ]
}
```

A course with no `specs/content/<course>/figures/` manifest at all contributes
`figures: {prompt_only:0, generated:0, placed:0}` and an empty `figures_pending` - never an
error (edge case, US4 AS2). `figures_pending` entries carry `{course_code, unit_no, topic,
figure_id}` for the human-readable "grouped by course, unit, and topic" list (FR-031).

**`depth_check` (implementation drift, T046)**: three values, not two -
`'pass' | 'fail' | 'not_applicable'`. `'not_applicable'` covers every case
`check-unit-depth.mjs` itself treats as out of scope and silently skips: the unit folder has
no `index.mdx` yet, `index.mdx` is `coming_soon: true`, the course has no `content-spec.md`,
the spec has no `## Unit N` subsection, or that subsection has no `### Sub-topic checklist`
table. `authored` is `false` in exactly the first two of those cases (no `index.mdx`, or
`coming_soon`); it is `true` for the remaining `not_applicable` cases (the unit IS authored
content, it just isn't in scope for the depth standard yet - e.g. EFMP-301's grandfathered
units) and for every `'pass'`/`'fail'` unit. This mirrors `checkUnitVerdict()`
(`scripts/lib/unit-depth.mjs`) exactly - the report never invents a fourth state or collapses
`not_applicable` into `pass`.

### Extended content-index record

`scripts/build-content-index.mjs`'s existing per-topic record gains two fields:
`self_assessment_count` (research.md R5), computed via the shared
`scripts/lib/mdx-sections.mjs#countChecklistInSection()` helper extracted from
`check-unit-depth.mjs`; and `topic_no` (implementation drift, T046 - not originally listed
here), read straight from the topic file's own front matter, needed by the Progress area
(FR-004) to key a student's `self_assessment_checks` rows to the right topic record (the
existing `unit_no`/`kind` fields alone don't disambiguate between a unit's several topics).
Both are `null` on every non-`kind: 'topic'` record. No other existing consumer of
`content-index.json` (Spec 003's assignment picker, Spec 004's Progress area) is affected -
both fields are additive.

### Catalog copy and catalog-edit form (T038, implementation detail)

`scripts/build-content-index.mjs` also copies `catalog/courses.json` verbatim to
`static/catalog-courses.json` at build time (same `static/*.json` convention). The
catalog-edit form (`admin/overview.tsx`) lets the owner edit one course's `title_en`,
`title_ur`, `credit_hours`, and `category` fields (the four free-text/short fields on a
`CatalogCourse` row - `code` itself is the selection key and is not editable, since changing
it would silently orphan every reference to the old code) and downloads a fully-formed
replacement `courses.json` with only that one course's row patched - the rest of the file is
passed through unchanged.

## State transitions

- **Self-assessment check**: `checked` toggles `false <-> true` freely (idempotent, no
  lifecycle); `item_text_snapshot` only advances forward, on a write the student makes.
- **Content feedback**: `open -> {planned, resolved, declined}`, `planned -> {resolved,
  declined}`, `{resolved, declined} -> open` (reopen). No other edge is legal (enforced by the
  guard trigger, not merely the UI).
