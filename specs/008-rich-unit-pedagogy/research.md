## R1 — Opt-in predicate for the new unit shape

**Decision**: A unit is evaluated on the new-shape rules **iff** both signals are present:
(a) at least one `topic-*.mdx` file in the unit folder, **and** (b) a `### Topic list` table in the
course content-spec's `## Unit N` subsection. If exactly one signal is present, or the topic-file
count differs from the `### Topic list` row count, the depth gate **fails** with a message naming the
mismatch — it never silently chooses a layout.

**Rationale**: Directly mirrors Spec 007 R4 (a unit is in depth-gate scope iff its subsection has a
`### Sub-topic checklist`). Two agreeing signals — one on disk, one in governance — make an
accidental half-migration a loud CI failure rather than a silent wrong-layout evaluation. Entry into
new-shape scope is irreversible (a unit cannot silently regress to legacy), which protects the
standard the same way 007's does.

**Alternatives considered**: a new front-matter marker (`layout: topic`) — rejected: a fourth
opt-in mechanism, and 007 explicitly avoided a new marker; a single filesystem signal — rejected:
gives no loud failure when the governance declaration is missing, and the gate needs the
`### Topic list` anyway to check the checklist→topic partition.

## R2 — Topic file naming

**Decision**: `topic-NN.mdx`, zero-padded single ordinal (`topic-01.mdx`, `topic-02.mdx`, …). The
display label ("Topic 1.1 — …") comes from `title` and the `topic_label` front-matter field, not the
filename.

**Rationale**: `sidebars.ts` is a single `{type:'autogenerated', dirName:'.'}`; siblings sort by
`frontmatter.sidebar_position` then filename. The repo convention (Specs 006/007) is filename/folder
order and **no `sidebar_position` in unit files**. Zero-padded single ordinals sort correctly to 99
topics. `topic-1-1.mdx` reintroduces the `topic-1-10 < topic-1-2` lexical bug and duplicates the
unit number the folder already carries.

**Alternatives considered**: `topic-1-1.mdx` (matches the owner's "topic 1.1" phrasing) — rejected
for the sort bug + redundancy; `sidebar_position` on every topic file — rejected: breaks the
established "no `sidebar_position` in content" convention and the `check:add-course` guard's spirit.

## R3 — The nine-part topic cycle headings

**Decision**: A fixed, ordered set of canonical `##` headings, checked for presence **and order**:
`## A real classroom situation` → `## Explanation` → `## Activity: <name>` → `## Check your
understanding` → `## Summary` → `## Self-assessment checklist` → `## Try this at your practicum
school` → `## Summative task` → `## Further reading`. Per-part minimums: formative ≥ 3 top-level
numbered items; checklist ≥ 3 `- [ ]` items; further reading ≥ 1 citation/link line. Full contract:
`contracts/topic-cycle.md`.

**Rationale**: Plain, translation-friendly wording keeps the student register (Art. III.1) and helps
per-file EN↔UR heading-vector parity (a fixed order means the parity gate has a stable target).
Canonical text makes each section mechanically checkable (`^##\s+Explanation\s*$` etc.). `## Activity:`
is matched as a prefix (`^##\s+Activity[:\s]`) so the author can name the activity.

**Alternatives considered**: author-chosen heading text with a semantic tag — rejected: not
regex-checkable and drifts across units; a custom MDX component per cycle part — rejected: adds a
rendering dependency and six unused components already exist; folding the cycle into `###` under one
`##` per topic inside `index.mdx` — rejected: the owner chose per-topic files.

## R4 — End-of-unit matter file

**Decision**: A new file `unit-assessment.mdx` (not a repurposed `summative.mdx`). Skeleton:
`## Unit summary` → `## Summative assessment` with `### Multiple-choice questions (MCQs)` (exactly
10 numbered), `### Restricted-response questions (RRQs)` (exactly 10), `### Extended-response
questions (ERQs)` (exactly 5) → `## Answers and marking guidance` (final section). Optional
`unit-teacher-notes.mdx` (renamed from `teacher-notes.mdx`) holds teaching strategies + practical
work and sorts after the topics. Contract: `contracts/end-of-unit-assessment.md`.

**Rationale**: A distinct name makes the file's role unambiguous and lets `validate-content.mjs`
forbid the legacy pooled files in a new-shape unit (blocks half-migration). `unit-` prefix on the
teacher-notes file makes it sort after `topic-*` rather than between `index` and `topic-01`.

**Alternatives considered**: reuse `summative.mdx` — rejected: overloads a legacy name and confuses
the legacy/new-shape branch in the validator; make `unit-teacher-notes.mdx` required — rejected: its
content is Art. III.6 guide-fidelity material, present only when the guide supplies strategies.

## R5 — End-of-course matter file

**Decision**: A **new course-level** `course-review.mdx` (sibling of `course-overview.mdx`), its own
front-matter schema (`course-review.schema.json`) and body contract
(`contracts/end-of-course-review.md`). It carries `sidebar_position: 900` — the **only** sanctioned
`sidebar_position` in content — so it sorts after the last unit. Skeleton: `## Course summary` →
`## Practice questions` (MCQs/RRQs/ERQs) → `## Project ideas for your practicum school` →
`## Answers and marking guidance` (final).

**Rationale**: `course-overview.mdx` has a distinct schema and purpose (course-wide items linked
*from* units); overloading it would blur both. Course-folder children sort lexically today
(`course-overview` before `unit-01`); a bare `course-review.mdx` would land between them, so it needs
one explicit position. Documented in the style guide as the single exception.

**Alternatives considered**: extend `course-overview.mdx` — rejected (schema/purpose mismatch); a
`zzz-course-review.mdx` filename hack to force sort order — rejected: uglier than one documented
`sidebar_position` and confusing in the sidebar tree.

**Scope note**: authoring EFMP-302's *actual* `course-review.mdx` is follow-up (FR-006 says "MAY");
Spec 008 ships the contract, schema and gate support. A course review over six units where five are
still legacy is premature.

## R6 — The answer-key policy exception

**Decision**: `check-no-answer-keys.mjs` gains one tightly-bounded allowance. The three **prose**
patterns (`\banswer\s*key\b`, `\bmarking\s*scheme\b`, `\bcorrect\s*answer\b`) are suppressed **only**:
in a file whose path matches `(?:^|/)(unit-assessment|course-review)\.mdx$`; **only** on lines after
a line that equals exactly `## Answers and marking guidance` (case-sensitive, no trailing text, after
`.trimEnd()`); **only** when no `^##\s` heading follows that line; **only** when exactly one such
heading exists in the file (`>1` → error; `0` → whole-file scan). The four **front-matter key**
patterns (`answer_key:` / `answers:` / `marking_scheme:` / `rubric_answers:`) still fire everywhere,
including inside the block. For `build/` HTML, suppress only the prose patterns for routes whose last
segment before `index.html` is `unit-assessment` or `course-review` (and their `/ur/` mirrors).
`EXCLUDE` (`style-guide.md`) unchanged. The JSON-Schema `not/anyOf` front-matter ban is **not**
relaxed.

**Rationale**: The book is a primary self-study resource (Art. I.1); a chapter-end bank with no
self-check is inert. The exception is made non-exploitable by five independent constraints (exact
heading, two-file whitelist, must-be-final-section, ≤1 per file, front-matter ban retained). It is
bounded and reversible.

**Alternatives considered**: keep answers out of the rendered book (teacher-only / git-ignored) —
rejected: defeats self-study for the majority not in a teacher-managed class; answers only in
`teacher-notes.mdx` — rejected: still needs the gate relaxed and mixes keys into teaching guidance.
Recorded as the one Complexity Tracking entry in `plan.md` and as an Art. V.2 amendment (FR-024).

## R7 — Figure marker grammar

**Decision**: An MDX comment at the insertion point:
`{/* FIGURE[fig-U<unitNo>-<seq>]: <generation prompt>; alt: <alt text> */}`. Regex:
`/\{\/\*\s*FIGURE\[(fig-U\d+-\d+)\]:\s*([\s\S]+?);\s*alt:\s*([\s\S]+?)\s*\*\/\}/g`. `<seq>` is a
unit-scoped integer sequence (`fig-U1-1`, `fig-U1-2`, …); the `U<n>` MUST equal the folder unit
number; `<prompt>` ≥ 10 non-space chars; `<alt>` non-empty. Markers are comments — they never render.

**Rationale**: MDX comments are invisible in the built site (FR-012) and diff cleanly in Git. A
single-line grammar with `; alt:` as the separator is easy to author and to parse. Unit-scoped IDs
match the example shown to the owner and keep IDs short and stable across a topic re-order.

**Alternatives considered**: a `<TeachingImage prompt alt />` component rendering a placeholder box
— rejected: adds a component + CSS + swizzle and shows scaffolding in production; front-matter
`figures: [...]` array — rejected: divorces the prompt from its insertion point; topic-scoped IDs
(`fig-U1-1-2`) — rejected: longer, and they churn when a sub-topic moves between topics.

## R8 — Figure manifest

**Decision**: `specs/content/<course-code>/figures/unit-NN.md`, one pipe table
`| Figure ID | Topic | Prompt | Alt text | Status |`, `Status ∈ {prompt-only, generated, placed}`
(every row `prompt-only` in this feature — nothing is generated). `check:figures` asserts: every
`topic-*.mdx` has ≥ 1 marker; marker set == manifest ID set in both directions; each manifest row's
`Topic` equals the `topic_label` of the file its marker sits in; no blank cells; `Status` in enum.
For `translation_status: reviewed` bilingual units, the UR `topic-*.mdx` must carry the same marker
IDs (markers are comments, so heading-vector parity does not cover them); `draft` units are skipped.
Contract: `contracts/figures-manifest.md`.

**Rationale**: The manifest is the single place a later image-generation pass reads its work queue,
and the cross-check catches a marker added without a manifest row (or vice-versa). Living under
`specs/content/` (not `docs/`) keeps it out of the render path, exactly like `coverage/` and
`sources/`.

**Alternatives considered**: no manifest, gate reads markers only — rejected: no queue for the
later generation pass and no place to track per-figure status; manifest as JSON — rejected: the
repo's governance tables are all Markdown pipe tables (`tasks.md`, `coverage/`, `sources/`).

## R9 — Reading-minutes band re-baseline

**Decision**: The `**Depth budget**` line becomes `N sub-topics; T topics; A–B reading-min`. `A–B`
is the target band for the **sum** across `index.mdx` + every `topic-*.mdx` + `unit-assessment.mdx`
(+ `unit-teacher-notes.mdx` when present). `N` and `T` stay advisory (not gated). Expect ~2–3× the
legacy band; EFMP-302 Unit 1 moves from `45–70` to a value set from the actual drafted total
(estimated ~100–150). `content-spec-v3.md` publishes a typical per-topic band (~12–25 reading-min)
as authoring guidance.

**Rationale**: A nine-part cycle per topic plus a 25-item unit bank is inherently longer than the
legacy pooled shape; keeping the old band would fail every conforming draft. Summing over the
new-shape file set (the exact set the layout defines) keeps the check meaningful. Only the band is
gated so the count figures can guide without being brittle.

**Alternatives considered**: per-topic bands enforced individually — rejected: over-constrains a
topic that legitimately needs more depth; keep the count gated too — rejected: 007 already made the
sub-topic count advisory for the same brittleness reason.

## R10 — Coverage matrix v2

**Decision**: `contracts/coverage-matrix-v2.md` supersedes 007's `coverage-matrix.md`. `File` enum
becomes the dynamic new-shape set: `index.mdx`, `topic-01.mdx … topic-NN.mdx`, `unit-assessment.mdx`,
`unit-teacher-notes.mdx`. `Section` maps a sub-topic to its topic file **and** the exact heading —
normally a sub-heading under that topic's `## Explanation`. New invariants: **(a) every `topic-NN.mdx`
must be named by at least one coverage row** (no unreferenced topic); **(b) for every checklist ID,
at least one coverage row names the exact `topic-NN.mdx` its `### Topic list` row assigns it to** —
the coverage matrix and the declared partition must agree, and a disagreement is a **hard failure**
(the gate scripts are binary — there is no non-failing "finding" channel). Extra rows for the same
ID naming other files (e.g. reinforcement in `unit-assessment.mdx`) are allowed and ignored by
invariant (b). The sources-consulted contract is unchanged; coverage↔sources mutual consistency
(every cited `Source` is a `Key`; every non-`no-external-source` `Key` is cited) is unchanged.

**Rationale**: The matrix must point at the file that now teaches each sub-topic; invariant (a)
catches a topic file that exists but teaches nothing on the checklist, and invariant (b) catches the
matrix and the `### Topic list` drifting out of agreement (added by /sp.analyze remediation U2).
Reusing the sources contract keeps the citation machinery identical to 007.

**Alternatives considered**: keep the 007 five-file `File` enum and map every sub-topic to
`index.mdx` — rejected: `index.mdx` is now just the opening, it teaches nothing; a separate per-topic
coverage file — rejected: multiplies governance files with no gain.

## R11 — `course-review.schema.json`

**Decision**: New JSON Schema. `required: [title, course_code]`; `course_code` pattern
`^[A-Z]{2,4}-[0-9]{3}(--)?$` (as elsewhere); optional `sidebar_position` (number),
`translation_status` (`enum [draft, reviewed]`), `bilingual` (boolean), `resources[]` (`{ref, type}`,
as on `course-overview`); `additionalProperties: true`; the same `not/anyOf` answer-key **key** ban
as the unit and course-overview schemas. Registered in `validate-content.mjs` via a
`checkCourseReview(courseDir, courseCode)` that mirrors the existing `checkOverview` (validate front
matter, confirm `course_code` matches the folder). Mirrored to repo-root `contracts/`.

**Rationale**: `course-review.mdx` *does* carry front matter (unlike the checklist/coverage/sources
tables), so a JSON Schema applies, consistent with `course-overview.schema.json`. The key ban must
be present because this is one of the two files where prose answer material is allowed — the ban
keeps that to *prose*, never structured front-matter keys.

**Alternatives considered**: reuse `course-overview.schema.json` — rejected: different required set
(`credit_hours`/`category` are mandatory there, meaningless here) and different purpose.

## R12 — Authoring skill packaging

**Decision**: One Claude Code skill at `.claude/skills/author-unit/` (`SKILL.md` + `references/`),
rewritten in place. **No sub-agent wrapper.**

**Rationale**: The workflow is one research → backward-design → draft → self-review → run-gates loop
that needs the harness's own `WebSearch`/`WebFetch` for source verification and the iterative
"run the gate, read the failure, fix, re-run" cycle in the main loop. A sub-agent isolation boundary
would lose the interactive source-verification and the gate-fix loop and buys nothing — the skill is
already invocable by phrase and version-controlled. Mirrors Spec 007 R10 / ADR-0010.

**Alternatives considered**: a parallel `restructure-unit` sub-agent — rejected: duplicates the
skill's references and loses the tool loop; a method document instead of a skill — rejected: 007
already chose a skill for the same reasons.

## R13 — Search index (`build-content-index.mjs`)

**Decision**: Extend the walk: for a new-shape unit, index each `topic-*.mdx` with `kind: 'topic'`
and `unit-assessment.mdx` with `kind: 'assessment'` (permalink
`/${sem}/${course}/${unit}/${basename}`); at course level, index `course-review.mdx` with
`kind: 'course-review'`. Legacy units keep the existing `KIND_FILES`
(`activities`/`formative`/`summative`) path unchanged. Update any search-e2e assertion that counts
indexed docs.

**Rationale**: New-shape units have none of the legacy `KIND_FILES`, so their topic and assessment
pages would be unsearchable without this. The legacy path is untouched (SC-007).

**Alternatives considered**: leave the index legacy-only — rejected: makes restructured content
un-findable in offline search, a regression for readers.
