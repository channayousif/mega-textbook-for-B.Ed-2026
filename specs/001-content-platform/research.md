# Phase 0 Research: Bilingual Content Platform

**Feature**: 001-content-platform | **Date**: 2026-07-17

The SDD source (`SDD/001-content-platform.md`, `SDD/ROADMAP.md`) and Constitution v1.1.0 already lock the major stack decisions ("Decisions Locked In" in ROADMAP). This document resolves the remaining technical unknowns needed to design and build, records rationale, and lists alternatives considered. **All Technical-Context items are resolved — no NEEDS CLARIFICATION remains.**

> Version-sensitive detail (exact i18n keys, plugin config, sidebar autogen syntax) MUST be verified against current Docusaurus v3 docs at build time (SDD F1). Use Context7 (`/facebook/docusaurus`) during implementation rather than trusting snapshots here.

## R1 — Framework: Docusaurus v3 (classic preset, TypeScript)

- **Decision**: Docusaurus v3 with the classic preset, TypeScript config (`docusaurus.config.ts`, `sidebars.ts`).
- **Rationale**: Locked by Constitution Art. V.1 and ROADMAP decision 1. First-class i18n with RTL, MDX components, autogenerated sidebars from folder structure, static output deployable to free tiers — a direct match for every functional requirement. TS template gives typed component props for the five MDX components.
- **Alternatives considered**: Astro Starlight (excellent i18n/RTL, but smaller MDX-component ecosystem and would break the constitutional lock-in); VitePress (weaker i18n RTL story); hand-rolled Next.js (violates "one course = one content module" simplicity and low-maintenance goal).

## R2 — i18n & RTL for Urdu

- **Decision**: Two locales — `en` (default, `direction: ltr`) and `ur` (`direction: rtl`). Urdu content mirrored under `i18n/ur/docusaurus-plugin-content-docs/current/…`. Per-page language toggle via the navbar `localeDropdown`. RTL handled by Docusaurus setting `<html dir>` per locale plus `[dir='rtl']` overrides in `custom.css`.
- **Missing-Urdu fallback** *(clarification 2026-07-17, Q1 → A)*: when a unit has **no `ur` file at all**, Docusaurus' default-locale fallback serves the English body under the `/ur/` route; the page MUST show a prominent `<TranslationStatusBadge variant="untranslated"/>` banner ("Urdu translation not yet available"). This differs from `translation_status: draft` (a UR file exists → show it under a "draft translation" badge, FR-003). Net: the `/ur/` route never dead-ends and English is never silently presented as Urdu.
- **Rationale**: Native Docusaurus i18n gives per-locale routing (`/` and `/ur/`), automatic `dir` attribute, a built-in toggle, and built-in default-locale fallback for untranslated pages — satisfying FR-001/FR-002/FR-003 and SC-001 with zero custom routing. Mirrored folder structure keeps EN/UR section parity auditable (see R4 parity gate).
- **Alternatives considered**: Single-page runtime language switch via React state (loses per-locale URLs, SEO, and static-search indexing per language); third-party i18n lib (redundant — framework provides it); a standalone "coming soon" UR placeholder with no English body (rejected in clarification — hides available content and adds a route type).
- **Verify at build**: exact `i18n` config block, `htmlLang`/`direction` keys, and the untranslated-page fallback behavior against current v3 docs.

## R3 — Urdu webfont (Nastaliq)

- **Decision**: Self-host **Noto Nastaliq Urdu** (WOFF2, subset to Urdu range) under `static/fonts/`, `font-display: swap`, with a Naskh fallback (Noto Naskh Arabic) and system fallback. Tune `line-height` (~2.0–2.2) for Nastaliq stacking in `[dir='rtl']` rules.
- **Rationale**: FR-002 requires an appropriate Nastaliq/Naskh webfont with a fallback and legible line spacing. Self-hosting (vs Google Fonts CDN) keeps the site free-tier and privacy-simple, avoids a third-party request on slow connections, and is compatible with the low-bandwidth budget when subset. Nastaliq needs generous line-height or glyphs collide.
- **Alternatives considered**: Jameel Noori Nastaleeq (higher fidelity but licensing/size concerns and larger file); Google Fonts CDN link (extra origin, blocked-request risk, slower on 2G); relying on device fonts (inconsistent Nastaliq availability on low-end Android).
- **Budget note**: subset + WOFF2 + lazy is required to respect the < 200 KB content budget (SC-002); font weight counts against first load, so load one weight.

## R4 — Front-matter validation (build gate)

- **Decision**: Node ESM script `scripts/validate-content.mjs` using `gray-matter` (parse) + `ajv` (JSON-Schema validation) against `contracts/unit-frontmatter.schema.json`. Walks `docs/**` and `i18n/ur/**`, fails non-zero with a per-file message naming the missing/invalid field. Wired as `npm run validate:content` and a required CI step before build. **Beyond schema checks, the same script enforces the structural rules below**, including the EN↔UR parity gate.
- **EN↔UR structural parity gate** *(clarification 2026-07-17, Q2 → C — fully build-enforced)*: for any unit whose UR `translation_status` is `reviewed`, the validator MUST fail the build when the EN and UR versions diverge in (a) section-file presence (both sides have the same five files) or (b) heading structure — i.e. the ordered sequence of Markdown heading levels/counts per file must match. Draft units (`translation_status: draft`) and units with no UR file yet are **exempt** from the heading-parity gate (they instead carry the badge/banner from R2/FR-003). Heading extraction: parse each file's body (strip front-matter/code fences) and compare the heading-level vector EN vs UR; a mismatch names the file and the first divergent heading position.
- **Rationale**: FR-009 / SC-007 require publishing to be blocked 100% of the time when required traceability metadata is missing; FR-001 (clarified) requires reviewed bilingual units to be structurally parallel so an untranslated/half-translated unit cannot ship as "reviewed". A schema contract makes required vs optional explicit and shape-checks optional fields only when present (SDD F3). Comparing heading vectors (not prose) is language-agnostic and avoids false positives from legitimate translation differences. Auto-discovery by folder walk means new courses are covered with no code change (FR-005, SC-006).
- **Alternatives considered**: editorial-only parity (rejected in clarification — no automated guarantee); full prose/paragraph diffing (brittle, fights idiom/sentence-splitting, false positives); Docusaurus front-matter schema plugins (limited cross-field/custom rules); remark/MDX lint plugin only (couples validation to build internals, harder to run standalone in CI); Zod instead of ajv (fine, but JSON Schema doubles as the published contract artifact).

## R5 — Bilingual local search

- **Decision**: `@easyops-cn/docusaurus-search-local` (offline, indexes all locales, supports CJK/RTL-friendly tokenization) configured to index both `en` and `ur`.
- **Rationale**: FR-006 / SC-004 require full-book search in both languages with no hosted dependency (Algolia is explicitly "optional later"). This plugin builds a static index per locale at build time — free-tier friendly and works offline-tolerant per Art. V.5. Un-authored "coming soon" units are **excluded from the index** (clarification 2026-07-17) so empty placeholders never surface as results; they stay visible in the sidebar marked "coming soon" (no dead ends, SC-005).
- **Alternatives considered**: Algolia DocSearch (hosted dependency, application process, not free-tier-guaranteed — deferred to backlog); `docusaurus-lunr-search` (weaker multi-locale/Urdu tokenization); native theme local search (English-tuned tokenizer, poorer Urdu matching).
- **Risk/verify**: Urdu tokenization quality — SDD step 6 says "verify Urdu tokenization acceptably matches." Acceptance measured against SC-004 (95% of searches return ≥1 relevant result); if inadequate, evaluate custom tokenizer/segmenter as a follow-up.

## R6 — Handout delivery (print stylesheet)

- **Decision** *(clarification 2026-07-17, Q3 → A)*: **No build-time PDF pipeline and no committed `.pdf` artifacts.** Each `activities.mdx`, `formative.mdx`, and `summative.mdx` page carries a `<PrintHandout/>` control (button) that calls `window.print()` against a dedicated A4 print stylesheet (`@media print` + `@page { size: A4; margin: … }`). The reader's browser produces the PDF via its native "Save as PDF"/print dialog. The print CSS hides chrome (navbar, sidebar, footer, TOC, the button itself), sets an A4-safe content width, and preserves RTL/Nastaliq for Urdu handouts.
- **Rationale**: FR-011 / SC-009 require a clean A4 printable with no clipped content — not necessarily a stored file. A print stylesheet satisfies that with far less machinery: no headless-Chromium render step in CI, no generated binaries to keep in sync with content edits, and it inherits the exact on-page styling (fonts, RTL, MDX components) already loaded. It is also the lowest-bandwidth option (nothing extra shipped). Matches the explicit clarification.
- **Alternatives considered**: Build-time Playwright/Puppeteer → `static/handouts/*.pdf` (rejected in clarification — extra toolchain, committed binaries drift from content, heavier CI); `md-to-pdf` standalone (same drift/toolchain cost); LaTeX pipeline (overkill, poor Urdu/MDX-component support). A generated-PDF pipeline remains a possible **later** enhancement only if pixel-exact offline files become a hard requirement — out of scope here.
- **Safety gate**: the button appears only on the three public framing files; `teacher-notes.mdx` and any answer-key content are never in the printable set (FR-012). Because printing is client-side from already-public pages, no new exposure surface is introduced. Validation still forbids answer-key front-matter fields (R4).
- **Verify at build**: print-preview each of the three files at A4 in Chromium/Firefox — no clipped content, chrome hidden, Urdu RTL correct (Playwright can drive `page.pdf()`/print-emulation for an automated A4 no-clip check, R7).

## R7 — Testing & rendering verification

- **Decision**: Vitest (or Node's built-in test runner) for `validate-content` unit/fixture tests; Playwright for RTL correctness, narrow-viewport (no horizontal scroll), draft-badge visibility, and handout print rendering; `docusaurus build` (both locales) as the CI integration gate; Lighthouse (CI) for the performance/accessibility budget.
- **Rationale**: Directly exercises the acceptance scenarios (RTL render, build-fails-on-missing-field, A4 print) and the engineering review gate (Lighthouse pass, RTL verified) from Constitution Art. VII.
- **Alternatives considered**: Cypress (heavier for static-site checks); manual-only verification (fails SC-007's "100% of the time" guarantee — needs automation).

## R8 — 8-semester scaffold generation

- **Decision**: A machine-readable catalog `catalog/courses.json` (semester → courses with code, EN/UR title, credit hours, category, priority) derived from the ROADMAP board-scheme tables; `scripts/scaffold-catalog.mjs` generates the folder tree, `_category_.json` files, `course-overview.mdx` stubs, and placeholder `unit-NN` files with valid minimal front-matter and a "coming soon" marker for un-authored units.
- **Rationale**: FR-014 / SC-005 require all 8 semesters scaffolded with un-authored units clearly marked and zero dead ends, while FR-005/SC-006 require adding a course to be content-only. A generator seeded from one catalog file keeps the 40+ courses consistent and makes "add a course" a one-entry edit + re-run.
- **Alternatives considered**: Hand-creating ~40 course folders (error-prone, drift-prone); encoding the catalog only in the board DOCX (not machine-consumable at build). Open code discrepancies (GNAS, Pakistan Studies, Fehm-e-Quran, GSOS CH) follow the board scheme and stay tracked in `specs/gaps.md` until the curriculum owner resolves them.

## R9 — Deployment & CI

- **Decision**: GitHub Actions: `validate:content` → `docusaurus build` (both locales) → deploy preview on PR, deploy prod on merge to `main`. Primary host **Vercel** (ROADMAP decision-still-needed #1 names Vercel as acceptable); GitHub Pages viable as a free fallback. Supabase region choice (Mumbai `ap-south-1`) is noted for later specs and is out of scope here.
- **Rationale**: Constitution Art. V.6 (free-tier), NFR "deployable from `main` via CI". Static output makes host choice low-risk and reversible.
- **Open (non-blocking) decision**: final domain + host confirmation is a curriculum-owner decision (ROADMAP §"Decisions Still Needed"); does not block scaffolding or the golden unit. Default to Vercel preview + GitHub Pages fallback until confirmed.

## Implementation status note (2026-07-17)

- **Verified working**: the content-validation build gate (`scripts/validate-content.mjs`)
  passes on the authored golden unit and is covered by 10 passing Vitest fixtures
  (parity, glossary-ref, missing-metadata, weighting-sum). The scaffold generator
  (`scripts/scaffold-catalog.mjs`) materialises all 8 semesters (47 files) and the
  validator stays green afterwards. All Docusaurus config, MDX components, and CSS are in place.
- **App verified via dev server**: `npm run start` compiles the client successfully and serves
  **every route with HTTP 200 — EN and UR** (`/`, `/semester-1/efmp-301/`,
  `/semester-1/efmp-301/unit-01/`, `/ur/`, `/ur/semester-1/efmp-301/unit-01/`). The homepage
  renders the configured title. So the site, i18n locales, routing, MDX components, and content
  all compile and run.
- **Static build (`docusaurus build`) — RESOLVED.** The `require.resolveWeak is not a function`
  SSG failure was **not** an environment limit (it reproduced on GitHub Actions ubuntu too); it
  was a real config bug: **`"type": "module"` in package.json** broke Docusaurus's CommonJS
  server bundle during SSG. Removing it fixed the build (the `.mjs` scripts stay ESM by
  extension). A second, content bug then surfaced — the scaffold gave every course the same
  `Unit 1 (coming soon)` sidebar label, producing duplicate i18n translation keys that failed
  the `ur` build; labels are now course-code-prefixed and unique. `docusaurus build` now
  succeeds for **en + ur**, and CI (GitHub Actions) runs green end-to-end: build (both locales)
  + Lighthouse + the full Playwright e2e suite. A separate `webpack ProgressPlugin` schema error
  seen while pinning older Docusaurus lines was a version mismatch, avoided by coherent 3.10.2.
- **T026 note**: the initial `DocItem/Metadata` swizzle did not emit the `noindex` meta;
  replaced with an explicit in-content `<Head>` in scaffolded placeholders — verified that
  coming_soon pages are dropped from `build/search-index.json` while the golden unit stays
  indexed.
