## C1: The batch's tracker merge assumes append-only rows, but workers edit rows in place, so I-0015 misses most real conflicts
- **Kind:** brief / planner fix (crew fix)
- **Cause:** `mergeAppendOnly` (`scripts/crew/batch.mjs:81`) returns null unless every base line survives on both sides. Jobs replace rows (`G1`, `G2` evidence, the `**Unit N` status line), so sibling units touching different rows still fall through to a merge-fix job, and each merge can expose the next sibling.
- **Recurrence:** 7 exclusions and 1 five-fix ceiling in the window (118 and 13 total). Repeats 2026-11-06 C2, 2026-11-03 C5.
- **Evidence:** replay of the 20 tracker merges on `origin/main` since 2026-11-04 made by conflict fixes: `mergeAppendOnly` resolved 1 of 20, and a trial merge keyed on (Unit, Stage) found no differing edit to the same row in all 20. Caveats: those 20 are by selection the merges the resolver had already failed, and the trial compared rows only and was not run as a real merge. `job:gqur-301-u15-repair_en` used 5 fixes and is still `gate_red`; `job:gicp-400-u06-author` used 3.
- **Proposed home:** `scripts/crew/batch.mjs` and `resolveSharedConflicts`: merge course `tasks.md` by row key, and fall back to a merge fix only when both sides change the same row differently. Requeue `gqur-301-u15-repair_en` once live.
- **Signature:** `left out of the batch: <path> conflicts with main (<path>).; merge fix queued`
- **Registry:** evidence for I-0015. Its row still says `proposed`, though the code merged on 2026-11-01 (`e571fdf81`), so the survey should correct that as well.
