## C1: Harvester noise filter leaks decision prose, grep output, and serialized JSON containing "rejected" or "failed" into error clusters
- **Kind:** gate or check
- **Cause:** `LOG_ERROR` in `scripts/crew/intel.mjs` matches lines where `failed` or `rejected` appears within the first 60 characters (`.{0,60}\b(failed|rejected|denied|ENOENT|EACCES|timed out)\b`). When workers read architectural specifications, ADR summaries, prompt templates, or grep command results containing discussion of rejected alternatives ("Simplest and fully coherent. Rejected: it uses one subscription...", "Rejected by the owner...", "cross-issue writes failed with..."), line numbers with grep output (`11:  reason, cross-issue writes failed...`), or JSON/Python serialized field keys (`'FAILURE_MODES':'... rejected 5-hour...'`), these lines are captured as error signals. Although M2 added `reported, not failed` and leading `?` to `LOG_NOISE` (I-0019), it did not filter decision prose ("Rejected:"), grep line number prefixes (`^\d+:\s+`), or serialized string mappings.
- **Recurrence:** 5 log error clusters (2 recent in `maint-2026-w44-m1-review2`, 2 in `maint-2026-w44-m2`, 2 historical in `maint-2026-w43-m3`) and 1 PHR failure mode in 24 h.
- **Evidence:** log:maint-2026-w44-m1-review2.1.log; log:maint-2026-w44-m2.1.log; log:maint-2026-w43-m3.1.log; phr:history/prompts/general/20261050-recognise-quota-filter-harvester-noise.general.prompt.md; `scripts/crew/intel.mjs:72-74`.
- **Proposed home:** Harvester filter update in `scripts/crew/intel.mjs` (`LOG_NOISE`): add patterns to ignore lines where `rejected` or `failed` is part of design rationale (`\b(Rejected:|Rejected by)\b`), grep line numbers (`^\d+:\s+`), or JSON/dict serialized fields (`^['"][A-Z_]+['"]:`).
- **Signature:** `simplest and fully coherent. rejected: it uses one subscription, stops when that subscription hits`
- **Registry:** candidate I-0019 (extends proposed I-0019 to cover design prose, grep line numbers, and serialized string mappings).

## C2: Greedily matching base lines in mergeAppendOnly risks misaligning repeated lines during tracker three-way merges
- **Kind:** gate or check
- **Cause:** `mergeAppendOnly` in `scripts/crew/batch.mjs` splits base and side inputs by `\n` and scans base lines in forward order, advancing `i` on the first exact match (`line === b[i]`). If `base` contains duplicate lines (most commonly empty strings `""` between markdown sections or table blocks), an inserted line that matches a later identical base line matches prematurely. While PR #393 (`maint-2026-w44-m1-revise1`) fixed the silent drop of blank-line insertions caused by join-based equality, the greedy forward scan can still map insertions to the wrong index when identical lines appear multiple times in base.
- **Recurrence:** 1 PHR failure mode (`join-based equality drops blank-line insertions from one side silently`), 1 handoff note (`mergeAppendOnly matches base lines in order, first occurrence first`), and 1 survey risk handoff note (`M1 is the only medium-risk task: it writes course tasks.md files automatically...`) in 24 h.
- **Evidence:** phr:history/prompts/crew-maintenance/crew-maint-2026-w44-m1-revise1.misc.prompt.md; job:maint-2026-w44-m1; job:maint-2026-w44-survey; `scripts/crew/batch.mjs:81-105`.
- **Proposed home:** Crew fix in `scripts/crew/batch.mjs`: use longest common subsequence (LCS) or anchor matching on distinct non-empty lines (such as table pipes or headings) instead of first-occurrence matching on ambiguous blank lines.
- **Signature:** `failure modes observed: join-based equality drops blank-line insertions from one side silently.`
- **Registry:** matches proposed I-0015 (provides evidence / extends I-0015).
